# OpenCode Zen Step 5 provider headers

## Contract

The OpenCode Zen free tier is only served on the OpenAI Chat wire, and it rejects a request that is not both `stream: true` and carrying a non-empty `tools` array with `403 FreeTierError`. The `chat:opencode-zen-tcm` compatibility profile therefore declares one provider-private contract: an attempt against this provider always goes upstream as SSE. The client-facing response format is not part of that contract and still follows the client's own transport intent, so a `stream: false` client receives a buffered JSON body.

The client keeps sending whatever body shape it wants. RCC owns three adjustments inside the declared provider contract:

1. Provider transport forces `stream: true` and the SSE transport intent for this profile, before the wire leaves RCC.
2. Dynamic `x-opencode-session` / `x-opencode-request` identifiers are stamped per attempt.
3. The buffered client SSE replay is reduced back to the JSON body the client asked for when the client asked for JSON.

The forced upstream SSE, the dynamic identifiers, and the client-JSON collapse are all scoped to this declared provider-private contract. Anthropic Relay gains one separate general correction in its client-response projection, described in item 7 below; no other provider, protocol, or execution mode changes behavior.

## First divergence and owners

The configured provider `headers` already compile into `V3ResponsesProviderTarget.headers`. The OpenAI Chat builder in `provider_compat_shared.rs` drops that map when it builds the typed transport request. The Provider-owned `ProviderResponsesTransport::send_http` then applies configured headers only for Anthropic requests. The same selected target therefore has its configured headers in dry-run projection but not on an OpenAI Chat HTTP request.

The free tier additionally rejects static `x-opencode-session` / `x-opencode-request` placeholders. The upstream OpenCode client derives both identifiers per attempt: `x-opencode-session` uses `Identifier.descending` (`ses_` + inverted 12-hex timestamp + 14 base62 chars) and `x-opencode-request` uses `Identifier.ascending` (`msg_` + ascending 12-hex timestamp + 14 base62 chars). A configured constant is therefore wrong even when the header carrier works.

The minimal fix reuses the existing target-to-transport carrier, the existing dual-intent transport builder, and the generic HTTP send owner:

1. The Runtime OpenAI Chat transport builder converts `target.headers` into `V3ProviderRequestHeader` values and places them on the existing transport request.
2. Provider authoring validation rejects a configured header named `authorization` after trimming, case-insensitively. Provider HTTP send applies the remaining configured headers to non-Anthropic HTTP requests. Anthropic continues using its existing compatibility path. The resolved provider secret remains the sole source of the wire `Authorization` header.
3. Provider request projections redact configured header values. Names remain visible for diagnosis. This prevents arbitrary provider header values from entering dry-run/debug artifacts; transport still sends the original values.
4. The shared helper `stamp_opencode_zen_dynamic_request_headers` rewrites `x-opencode-session` and `x-opencode-request` with fresh schema-encoded identifiers at the transport-attempt boundary. It applies only to `provider_type == "openai_chat"` with compatibility profile `chat:opencode-zen-tcm`, deletes any configured placeholder first, and changes neither the body nor the wire model. Both the business transport builder and the startup probe call the same helper, so probes never carry a stale placeholder. Identifier state stays in control-space (an atomic counter plus the clock); no value is read from or written to the business payload.
5. In the same builder, `v3_provider_profile_requires_upstream_sse` forces `body["stream"] = true` and the SSE transport intent for that profile, whatever the client intent was. The response side is unaffected: the transport request and the client projection carry separate intent values.
6. Direct keeps its own response intent. When the client asked for JSON, the entry protocol is OpenAI Chat, and the selected provider carries the forced-SSE contract, the Direct kernel reduces the buffered, already-validated client SSE replay to one JSON completion through `collapse_direct_client_sse_to_json` and projects `content-type: application/json`. The reducer input is the already-projected, sealed `V3CommittedClientSseStream` that reached terminal validation and full buffering, not the raw provider response. The reduction keeps the representable Chat fields intact: `system_fingerprint` and envelope extensions on the completion, choice-level extensions such as `logprobs`, and unconsumed delta extensions on the message object. Reducer failure is a typed internal Runtime failure; no partial frame reaches the client. Any other provider keeps the prior pass-through behavior.
7. Anthropic Relay already tracked the client's real transport intent for the client body but projected the client response envelope with a hardcoded SSE intent. It now passes the real client transport intent into `project_v3_anthropic_client_response_for_provider`, so a `stream: false` Messages client receives one JSON message. This is a general Anthropic projection correction on the SSE response branch; it is not scoped to the Zen contract, and every Anthropic Relay caller that reaches this branch uses the client's real intent.
8. Responses Relay keeps its provider-request transport-intent guard. Instead of skipping the check when the profile forces SSE, it retargets the expected value to `Sse` for that profile and leaves the client projection on the client's own intent, so the guard still fires if the forced-SSE contract is ever broken in code.

The feature graph is the Direct JSON success subpath. Its single input is already classified as an OpenAI Chat JSON client request with the selected `chat:opencode-zen-tcm` provider contract; the graph then shows the profile decision, transport request, provider attempt, runtime terminal validation and sealing into `V3CommittedClientSseStream`, and the final JSON collapse. The collapse reads the sealed client replay, not raw provider bytes. Config compilation and target selection remain with their existing owners. Model binding, retry behavior, and provider selection are unchanged. The Provider transport remains generic and does not branch on provider ID. Provider-private body adjustments stay at the transport boundary, which is the same place the existing DeepSeek compat adjustments live. A successful raw provider response returns to the existing Runtime response projector. HTTP/transport failures enter the existing typed Error/recovery chain and never project as a successful payload, so a `403 FreeTierError` breaks the client transport instead of returning an error body. Cancellation or client disconnect terminates the attempt as the existing cancellation outcome. Reselection, exhaustion, and client transport behavior remain owned by existing Runtime/Error nodes. The Anthropic client-intent projection and Responses Relay transport-intent guard are separate Relay object flows, bound by their existing `v3.anthropic_relay.controlled_runtime` and Responses Relay caller chains; they are not collapsed into the Direct-only graph.

## Verification contract

- Runtime builder test: selected target headers reach the typed OpenAI Chat transport request, and the `chat:opencode-zen-tcm` profile replaces static `x-opencode-session` / `x-opencode-request` placeholders with values matching the `ses_`/`msg_` 12-hex + 14-base62 shape. A non-OpenCode profile and a non-Chat protocol leave the configured values untouched.
- Forced-SSE builder tests, both inside the mapped `test:v3-opencode-zen-provider-headers` filter: a `stream: false` client on the Zen profile reaches the wire with `body.stream == true` and SSE transport intent, and a `stream: false` client on a non-Zen profile keeps `stream == false` with JSON intent.
- Identifier helper test: ascending and descending encodings differ and are exact complements; consecutive `stamp` calls produce distinct session and request values.
- Probe builder test: an OpenCode Zen probe request carries generated identifiers rather than the configured placeholder.
- Provider transport loopback test: configured `x-opencode-*` headers reach the actual HTTP wire and the request contains exactly the secret-derived Bearer authorization. Provider request projection shows header names and redacted values.
- Provider authoring test: an `Authorization` entry in `headers` fails config validation before runtime.
- Post-install live delivery acceptance: authenticated curl through the installed entry, targeting the free-tier wire model with streaming and a non-empty `read` tool, returns a model answer from Zen and no `FreeTierError`. This is a task-specific runtime closeout, not a source test gate. A non-Zen control request receives no configured OpenCode headers in the controlled author test.
- Public-entry black box, part of the mapped `test:v3-opencode-zen-tcm-bridge-blackbox` target: the upstream peer rejects any request whose body carries `stream != true`, so the mapped gate cannot pass while the forcing regresses. Three `stream: false` clients, `/v1/chat/completions`, `/v1/responses`, and `/v1/messages`, each receive one success with `content-type: application/json` and the real model answer, while the captured upstream attempts all carry `stream == true` and one attempt per entry.
- Public-entry black box: the forced-SSE collapse keeps representable Chat fields for a JSON client. The upstream peer emits `system_fingerprint`, `service_tier`, choice-level `logprobs` across at least two chunks, and an unconsumed delta extension; the collapsed JSON client body must carry both logprobs observations in stream order and all other fields.
- Public-entry black box: an upstream `403 FreeTierError` never reaches the client as an error payload. The client either observes the transport break or receives no provider error body.
- Same-entry replay: consecutive requests carry different `x-opencode-session` / `x-opencode-request` values.
- A real upstream error remains an error; it does not become a model answer or trigger an unconfigured fallback.

## Scope

Allowed implementation owners are the existing OpenAI Chat Runtime transport adapter, the Provider header helper, the Direct kernel client-response projection, the Anthropic Relay client projection, the Responses Relay transport-intent guard, and the generic Provider HTTP transport, plus their focused tests. Architecture maps and this feature graph may be updated to bind the existing source and gates. The forced-SSE decision is scoped by the declared `chat:opencode-zen-tcm` profile; no other provider gains a stream rewrite or a client-body collapse. The locked Hub skeleton, Server, Virtual Router, Error chain, provider auth source, live configuration, and provider selection remain outside the author phase.

2. TO-BE DAG：最小但完整

从项目真实目标出发，只保留让 correctness、traceability、verifiability、acceptance、delivery 成立所必需的节点。优先复用现有 AppSDK lifecycle records 和 RouteCodex maps，不新增平行治理框架。

ONE CONDITIONAL SPINE

路径规则

  • Bug：进入 TB04 reproduction/root cause。
  • Feature：可跳过 TB04，但必须保留 acceptance 和 owner/map。
  • Docs / CI-only：在 TB09 声明不适用后，可走 TB10 acceptance、TB11 close。
  • Runtime：必须走 TB09A-B。
  • Release：走 TB09R1-R3，把 publish/tag/package receipt 回指 acceptance。

只列结构性差异。命名不同不算差异；“节点已经存在但缺少连接或证据”优先标为 binding/evidence gap，而不是要求重写代码。

4. Closure Violations

按 A-J 逐项判断。这里把“没有证据”与“没有证据绑定”分开：前者不能宣称完成，后者是当前最可修的流程缺陷。

PATH-SPECIFIC
检查判定证据与影响
A. Orphan Requirement 部分成立 Feature request 可以落到 docs/goals 和 PR，但没有统一 requirement record 强制下游 candidate/merge/delivery 反指，故路径可能断在 merge。
B. Orphan Implementation 成立 2个 function features 没有对应 verification feature，无法从 implementation 走到验证终端。
C. Unverified Implementation 成立 上述两个 function 是明确的 map-level unverified implementation；此外部分 runtime feature 只有 source/test，无 live replay。
D. Unbound Verification 成立 3个 verification features 没有 function owner，测试存在但无法知道它服务哪个 requirement/implementation。
E. Missing Acceptance 成立 Feature 路径缺统一 acceptance node；merge、CI 或 unit tests 不能替代用户目标满足。
F. Missing Evidence 系统性成立 PR body 证据字段不一致；30个 PR 中仅14个有 evidence、6个有 replay。部分是文字缺失，部分是实际交付证据缺失，需 receipt 区分。
G. Dependency Gap 成立 merge → delivery applicability 未统一；release SHA 未强制等于 verified main；13条 mainline edges pending。
H. Dead Node 未证明 没有足够证据判定某个节点删除后完全不影响 requirement/implementation/verification/delivery。不要把 orphan 直接等同 dead。
I. Cycle 未发现 当前观察到的边均可拓扑排序；问题在缺边和弱绑定，不是循环依赖。
J. Premature Closure 路径级成立 两个 closed P0 有强 receipt；若把只有 merge/test 证据的 runtime PR 视为已交付，则属于 premature closure。不能把所有 closed item 一律判错。
最危险的不是 open bug 数量。66 open、12 P0 是 backlog 风险；DAG 风险是某些 feature 已经 merge，但没有统一机制强制证明它是否还需要 runtime install、replay 和 user acceptance。

5. Minimal Migration Plan

顺序严格按“补 binding → 补 verification → 补 evidence → 补 edge → 补必要 node → 最后才考虑架构重构”。不改已经正确工作的 runtime 代码。

NO REWRITE
顺序动作为什么最小完成证据
1 把现有 issue/goal、candidate、review、merge、delivery、close 串成一条 record graph。 已有 AppSDK records，只是实际路径没有一致使用。 每个 id 可解析；candidate/reviewed/merge hashes 一致。
2 在现有 Goal/PR receipt 增加 delivery_class：docs_ci、runtime、release。 用一个枚举消除 merge 后是否继续交付的歧义。 分类缺失或 runtime/release 无下游 receipt 时 close gate 失败。
3 补 runtime/release 条件门：artifact SHA + install + restart + health + same-entry replay。 复用现有 verification map、lifecycle records 和 release workflow。 receipt 全部引用同一 main SHA/artifact hash；replay 引用原 requirement。
4 修 2个 orphan function 和3个 orphan verification。 只补缺失边或明确 terminal；不新增测试框架。 function → verification 双向可解析，或删除项有证据依据。
5 Merge receipt 绑定 completed main verification run；取消时重跑。 避免用 PR green 代替 post-merge tree 验证。 merge SHA == run SHA，run conclusion == success。
6 Release workflow 加 verified origin/main equality gate。 现有 release 结构保留，只加一个依赖检查。 release source SHA == verified main SHA，否则 fail closed。
7 逐条清理13条 binding_pending。 作为独立 map debt，不阻塞其他已完成 feature。 每条 anchored，或有明确 deferred owner/risk。
8 PR summary 保留，但 truth 指向 records。 不删除历史证据，不要求人工维护两套真值。 PR body 不再承担唯一 evidence carrier。
不做什么：不重写正确 runtime；不为每个 feature 建一套新状态机；不把所有 docs/CI 变更强制跑 install/replay；不删除历史 issue comments 和已有 evidence。

这些风险在补齐最小 DAG 后仍需单独管理；它们不是靠“多一个 review”就能消除。

7. Final Closure Criteria

一个 Feature / Bug 只有在适用的终态证据全部存在时才算闭合。条件节点按 delivery class 启用，不能用“不适用”掩盖真实 runtime 风险。

ACCEPTANCE GATE

通用必要条件

  1. Requirement 和 acceptance criteria 已记录并确认。
  2. Owner、scope、allowed/forbidden paths 和 map bindings 已锁定。
  3. Candidate exact SHA/tree 可追溯。
  4. Focused verification 和 architecture gates 对 exact candidate 通过。
  5. Independent review 对同一 candidate/tree 给出 PASS。
  6. Merge receipt 绑定 main SHA 和 completed main verification。
  7. Delivery class 已声明为 docs_ci、runtime 或 release。
  8. Acceptance 对照原始 requirement，而不是只看测试绿。
  9. Close receipt 能反向解析全部上游 records。
  10. Cleanup 只移除本轮资源，并留下 disposition。

按 delivery class 的 terminal

Class合法 terminal必须证据
docs_ci Merge + acceptance receipt scoped gates、review、merge SHA；install/replay 明确不适用。
runtime Acceptance replay + close receipt artifact hash、install、restart、health、same-entry replay，全部绑定 main SHA。
release Published release + acceptance receipt verified main SHA、release gates、tarball hash、tag、install/replay 或等价用户入口证据。
FAIL closed：任何 requirement 路径如果只能到达 merge、PR green 或 artifact upload，就不能宣称 Feature/Bug 完整交付。

审批判断

当前项目的主线工程能力已经存在，缺陷集中在“实际执行过的 DAG 没有被同一套 record graph 完整描述和验证”。最小改造应只补连接、条件门和 receipt；审批后先提交这份设计，再进入 gap 修复计划。

## L94-custom-tool-call-input-sse-events-not-provider-failure
- Trigger: live `/v1/responses` Relay fails with `response.custom_tool_call_input.delta is unsupported`, then VR switches/retries provider.
- Judgment: `response.custom_tool_call_input.delta/.done` are official OpenAI Responses events (openai-openapi spec) streaming the `input` of `custom_tool_call` output items; protocol truth, not provider failure. Same class as L93-reasoning-summary.
- Action: materialize at `responses_provider_event_codec.rs` (resp-side inbound provider-wire codec): `.delta` appends `delta` to matched item `input`, `.done` sets `input`; reuse `find_v3_runtime_responses_event_function_item_mut`.
- Anti-pattern: treating upstream custom tool events as provider health failure, fixing Error06 display, patching VR/provider config, or leaking Responses req fields into provider request.
- Boundary: unknown `response.*` events still hard-fail; no silent ignore.
- Evidence: red test with exact live error first, green after; live replay on installed binary (asxs gateway family with custom apply_patch tool) HTTP 201 with correct `custom_tool_call.input`.

## L94-route-classifier-keyword-weighted-score-threshold
- Trigger: keyword intent routes (web_search / search / longcontext) fail to bind to the right pool because text-intent detection is too coarse (single-shot STRICT_TERMS) or missing from the routing decision.
- Judgment: single-shot "any term matches → true" over-recalls and under-recovers in opposite directions; "verb+noun combination" explodes combinatorially. The right shape is **weighted score + threshold gate + strong override + negative context**.
- Action: `v3/crates/routecodex-v3-route-classifier/src/tools.rs::has_web_search_intent` — three strength tiers (Strong=1.0 core phrases, Medium=0.6 verb phrases, BrandWeak=0.4 brand-as-verb), threshold 0.6, strong override bypasses threshold; route.rs `classify_route` consumes the result with a guard that the turn is a user input turn without image attachment and without current-turn tool output. Dryrun tests (drive `classify_route` end-to-end with `RouteClassifierInput`) lock the keyword→route contract beyond the function-level unit test.
- Anti-pattern: ① padding STRICT_TERMS with single characters (`搜`/`查`/`上网`) — collapses to false positives on coding requests ("搜文件" must NOT trigger web_search); ② trusting the keyword path without a dryrun test that asserts the resulting `route_name` — the function passes in isolation but the wiring regresses silently; ③ letting VR/provider runtime reimplement intent detection — owners are the classifier crate alone.
- Boundary: ① do NOT add `metadata`/`previous_usage`/`session_scope` fields to `RouteClassifierInput` — previous-turn usage hint crosses the P0 control-plane isolation guard; ② brand-weak alone must never promote to web_search (single 0.4 < 0.6 threshold); ③ negative-context regex must suppress even strong hits ("don't search" / "不需要联网").
- Evidence: 9 unit tests on `has_web_search_intent` (strong/medium/brand-weak stack/brand-weak alone/negative context/case-insensitive/unrelated) + 6 dryrun tests on `classify_route` (strong→web_search / medium→web_search / double-weak→web_search / single-weak→non-web-search / negative→non-web-search / multimodal-outranks) → 25/25 green; live on installed `rccv3` 0.90.4244 with 5520 responses port: text containing "联网搜索" routes to `web_search:minimax_anthropic.MiniMax-M3 reason=pool:web_search`; control text without keyword routes to `pool:default`. Commits b5709a462 + bb687e854.

## L94-route-classifier-search-candidates-tools-default-cascade
- Trigger: a port whose search pool is empty (no search-capable upstream) fails to serve search continuation requests because `RouteClassification.candidates = [search, default]` skips the `tools` fallback that the VR could actually satisfy.
- Judgment: route-classifier's responsibility is candidate ordering; pool availability is VR's. The classifier must list every fallback route so VR can walk the candidate list in order — mirroring the existing longcontext cascade.
- Action: `v3/crates/routecodex-v3-route-classifier/src/route.rs::classify_route` candidates block — after the existing longcontext cascade, if `route_name == "search"` and `tools` is not already in candidates, push `"tools"`. `default` is appended unconditionally below as before.
- Anti-pattern: ① hardcoding fallback order into ALL routes — breaks the keyword→web_search contract when web_search routes accidentally include tools; ② expecting VR to re-derive fallback from capability rules — duplicates classifier logic and drifts; ③ silently downgrading `search` to `tools` without listing `tools` in candidates — VR has no signal to attempt tools.
- Boundary: the cascade only fires when `route_name == "search"`; `web_search` / `thinking` / `coding` / `tools` routes do NOT cascade to tools.
- Evidence: 3 dryrun tests (search-continuation candidates = `[search, tools, default]` / tools not double-inserted / non-search routes do not leak tools) → 28/28 green. Live pool-empty case untested in this round (no port currently lacks a search pool); coverage is at the candidate-list level which the VR honors.

## L94-p0-control-state-compile-time-guard
- Trigger: someone (often well-intentioned) wants to pass previous-turn usage / session scope / request metadata through a boundary that should only carry routing facts. P0 forbids control state in normal payload.
- Judgment: doc-comments alone decay. The right shape is **code-level friction** — adding a control-state field MUST touch the guard test, which forces an explicit ownership review at merge time.
- Action: in any crate that owns routing/classification decisions, enumerate the input struct fields in a destructuring expression inside a test (`let _ = (input.field1, input.field2, ...);`) and add a runtime blacklist check for forbidden names (`metadata`, `previous_usage`, `session_scope`, `control`, `control_state`, `raw_metadata`, `conversation_metadata`, `prev_usage`). The destructuring is the deliberate friction; the blacklist is the runtime net.
- Anti-pattern: ① doc-comment only — comments drift; ② a runtime-only check using reflection — fails to compile if a new field is added, but a reflection test is brittle and easily disabled; ③ letting the guard test become a TODO — the guard MUST fail the build when someone adds the forbidden field, not warn.
- Boundary: applies to ANY crate whose struct crosses into provider wire / client wire; the test MUST be co-located in the same crate so it ships with the gate.
- Evidence: `route_classifier_input_has_no_control_state_fields` in `v3/crates/routecodex-v3-route-classifier/src/tests.rs` — both compile-time destructure of all 9 fields and runtime blacklist; 29/29 green; commits b5709a462 + bb687e854.

## L94-live-replay-on-installed-binary-not-just-red-green
- Trigger: a routing/keyword/capability change passes unit + dryrun tests in isolation but the live binary still routes wrong because of an unrelated install gate (e.g., a sibling WIP change introduces forbidden wording) or the binary in PATH is stale.
- Judgment: the only authoritative runtime truth is the installed `routecodex` binary + its config + the live log. Build success + test green is necessary but not sufficient.
- Action: build → install via `npm run install:v3` (which runs all architecture gates; WIP unrelated changes can fail the gate) → `routecodex restart -c ~/.rcc/config.v3.toml` → grep `~/.rcc/logs/server-v3-*.log` for `route=<route>` and `reason=pool:<route>` on the test request → compare against a control request without the keyword to confirm the route diverges correctly.
- Anti-pattern: ① running only `cargo test` and calling it done; ② failing to stash unrelated WIP before install (the architecture gate is whole-repo and a stray WIP can fail install for an unrelated reason); ③ grepping logs without a control case — without the contrast you can't tell if the routing changed because of your fix or because of default config drift.
- Boundary: when other tasks have uncommitted changes in working tree that touch forbidden-wording patterns (`fallback`/`replay`/`sanitize`/`repair`/`run_.*pipeline`), stash them with `git stash push -u -m "wip-other" -- <paths>` before install; pop them after the live verification so the next task resumes cleanly.
- Evidence: 5520 responses port with input "帮我联网搜索一下 rust 1.80" → log line `route=web_search reason=pool:web_search target=minimax_anthropic.MiniMax-M3`; control input "用一句话解释 rust 所有权" → log line `reason=pool:default`. Both routes resolved correctly on installed `rccv3 0.90.4244` instance `v3-706cc8a89cd1abb671bf`.
